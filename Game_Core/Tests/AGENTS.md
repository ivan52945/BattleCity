# Tests — host-юнит-тесты ядра

doctest (vendored header, `doctest/doctest.h`), standalone CMake-проект:
платформенные пресеты не задевает. `cmake --build` гоняет тесты сам
(POST_BUILD) — упавший кейс роняет сборку; `ctest --test-dir Tests/build
--output-on-failure` — точечный прогон и CI (GitHub Actions: ubuntu
+ gcc, санитайзеры ON — там libasan есть, санитайзер-зависимые кейсы
ловят жёстко). Первый запуск:

```
cmake -S Game_Core/Tests -B Game_Core/Tests/build -G Ninja
cmake --build Game_Core/Tests/build
```

Политика процесса — раздел «Тесты» корневой карточки; почему так —
ADR-0009.

## Железный закон

Новый код — через красный: кейс на контракт пишется и запускается ДО
реализации (красный = не проходит или не собирается), затем
минимальная реализация до зелёного, затем рефакторинг. Кейс, зелёный
до реализации, test-first'ом не считается.

## Словарь

- **Шов** — публичная граница: API ядра; панельный двойник — через
  concept `Disp`. Тест живёт на шве, не во внутренностях (ADR-0004).
- **Мутант-мишень** — что именно ломаем для проверки кейса; кейс
  называет её в комментарии трассировки.
- **Выживший мутант** — сломали, а кейс-мишень не упал: кейс ничего
  не закрепил.

## Как пишутся кейсы

- Источник — контракт модуля: `README.md` + doc-комментарии
  заголовков (контракт метода живёт над методом). Ожидаемое —
  независимый источник (литерал, прорешанный пример, контракт),
  не пересчёт формулой кода.
- Техники чёрного ящика: эквивалентное разбиение + краевые значения
  (0, 1, N−1, N, N+1-й вызов), переходы состояний (включая
  невалидные), таблицы решений на комбинации условий.
- Один кейс — одно поведение; имя = сценарий; детерминизм
  (фиксированный сид `rand()`, где задействован).
- Трассировка: комментарий к кейсу называет пункт контракта и
  мутант-мишень.
- Идиом прохода — как в примере README:
  `for (s = p.start(); p.is_nEnd(); s = p.next())` — условие до тела,
  `next()` не вызывается за пределами окна.

## Мутационная проверка

Ломать `Inc`-заголовок точечно → сборка/прогон → кейс-мишень обязан
упасть → `git checkout -- <файл>`. Типовые мутанты: `>=` ↔ `>`, убрать
swap/флаг, офф-бай-один, условие `nullptr`. Выжил мутант — добавляй
кейс, а не ослабляй проверку.

## Чек-лист кейса

- [ ] Трассировка: пункт контракта + мутант-мишень
- [ ] Красный до реализации — или слом кейс-мишени (существующий код)
- [ ] Ожидаемое — из контракта, не пересчитано формулой
- [ ] Полная сетка зелёная (сборка POST_BUILD / ctest)

## Состав и ловушки

- `test_lobby.cpp` — сетка пула `Lobby` (20 кейсов); `test_map.cpp` —
  сетка карты (18 кейсов, обе панели-формы); `test_tank.cpp` — сетка
  танка (12 кейсов; вероятностные кейсы ИИ привязаны к сидам
  libc-rand — пересмотр при пункте V); `test_shell.cpp` — сетка
  снаряда (9 кейсов: полёт, ориентация, края, местность);
  `test_game.cpp` — оркестраторная сетка `GameT` (8 кейсов: порядок
  кадра, CS-окно по журналу событий, квоты, lull-дисциплина,
  friendly-fire). Сканы по авторской карте — общие, в `probes.hpp`.
  Двойник `fake_lcd.hpp` —
  записывающая панель под `Disp` (статический журнал blit'ов; журнал
  накапливает — `reset()` перед каждой фазой чтения). Новый модуль
  ядра — `test_<module>.cpp` + строка `core_test(...)` в
  `CMakeLists.txt` (ассеты линкуются каждому таргету).
- doctest: `CHECK`/`REQUIRE` не принимают `&&` («Expression Too
  Complex») — разбивать на отдельные проверки.
- mingw-w64 gcc без libasan: собирать с `-D TESTS_SANITIZERS=OFF`
  (опция OFF по умолчанию); на тулчейне с санитайзерами — включать.
- `-static` обязателен: чужой `libstdc++-6.dll` в PATH ловит
  STATUS_ENTRYPOINT_NOT_FOUND (как в Platforms/Host).
- Санитайзер-зависимые кейсы: мутант wrap'а (`map_at_wraps`) на mingw
  выжил — тихое OOB-чтение совпало по значению; на тулчейне с libasan
  этот кейс обязан ронять мутанта (ADR-0009).
- Кейс-переименование папок (tests → Tests) в один шаг Windows не
  даёт — через временное имя.
